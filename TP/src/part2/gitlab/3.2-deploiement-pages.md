# Déployer un site statique avec Pages (GitLab)

Avoir un livre de cuisine numérique, c’est bien. Mais le rendre joli et facile à consulter, c’est mieux !
GitLab Pages permet d’héberger simplement un site web statique à partir des fichiers de votre dépôt.

### Objectifs

* Ajouter un fichier de pipeline `.gitlab-ci.yml` dans le dépôt du livre collaboratif.
* vérifier la grammaire et l’orthographe des recettes avec Grammalecte.
* Déployer automatiquement un site statique avec GitLab Pages.
* Visualiser le site web hébergé par GitLab Pages.
* Itérer sur le contenu et affiner la configuration du pipeline.


---

## Etape 0 - Coordination avec votre équipe

<div class=warning>
Vous travaillez ici sur le dépôt collaboratif du livre de recettes. Assurez-vous d’être sur une branche dédiée et de vous coordonner avec vos camarades.
</div>

Avant de commencer à changer quoique ce soit, planifiez avec votre équipe la manière dont vous allez procéder. Qui va faire quoi ? Qui va relire les modifications avant de les fusionner dans la branche principale ? Et pour gérer ça n'hésitez pas à utiliser les issues de gitlab.

## Étape 1 — Créer le fichier `.gitlab-ci.yml`

La encore tout commence par la création d'un fichier `.gitlab-ci.yml` à la racine de votre dépôt. Ce fichier va definir l'ensemble des étapes qui seront executer en fonction des règles que vous allez établir.

Cette fois ci, il faut un pipeline à 3 étapes :

```yml
stages:
    - lint
    - build
    - deploy
```

A noter que l'ordre des étapes est important, le pipeline s'exécutera dans l'ordre où les étapes sont définies.

### Étape 1.1 - Étape de lint

L'étape de lint est essentiellement la même que celle que vous avez déjà mise en place pour votre dépôt personnel. Vous pouvez vous en inspirer et copier-coller le code dans votre nouveau fichier `.gitlab-ci.yml`. Attention cependant à eventuellement adapter les chemins si votre structure de dépôt est différente.

### Étape 1.2 - Étape de build

L'étape de build va permettre de générer le site statique à partir des fichiers markdown. Pour cela nous allons utiliser le générateur de site statique astrojs. Pour vous simplifier la tâche, nous avons deja préconfiguré une image docker contenant astrojs et un template de site web. Vous pouvez l'utiliser directement dans votre jb `image: registry.gitlab.com/à_compléter`.

Le job de build va donc ressembler à ça :

```yml
pages:
  stage: build
  image: registry.gitlab.com/à_compléter
  before_script:
    - npm install
  script:
    - npx astro build
```

<div class=warning>

Attention, `pages` est un nom spécial pour un job dans GitLab CI. Il permet à Gitlab de savoir que ce job est destiné à déployer un site avec GitLab Pages. Il est toutefois possible de le renommer, mais dans ce cas il faudra ajouter une configuration supplémentaire pour indiquer à GitLab que ce job doit être traité comme un job Pages.

</div>

Il ne reste plus qu'à indiquer à gitlab que le dossier `public/` généré par astrojs doit être sauvegardé en tant qu'artefact. Pour cela, on ajoute les lignes suivantes à notre job :

```yml
  artifacts:
    paths:
      - public
```

<div class=warning>
Attention, encore une fois, par defaut, Gitlab Pages attend que le dossier s'appelle `public/`. Si vous changez le nom du dossier de sortie, il faudra le spécifier dans la configuration du job.
</div>




### Étape 1.3 - Étape de déploiement

Et le déploiement alors ? Vous n'avez rien à faire de spécial pour cette étape.A partir de la, gitlab ce charge de tout du moins si vous avez bien nommé votre job `pages` et que vous avez bien spécifié que le dossier `public` doit être sauvegardé en tant qu'artefact. 

## Visualiser le site web et itérer

Une fois le pipeline terminé, vous pouvez visualiser votre site web en cliquant sur le lien dans la section **Pages** des paramètres du projet.


Que se passe t-il pour le site web si vous plusieurs de vos cammarades font des modifications en même temps ? Le site web est il mis à jour automatiquement ? Avec quelle version et quelle branche ?

<details>
Si vous n'avez pas configurer de règles particulières, le site web est mis à jour à chaque fois qu'une modification est poussée sur n'importe quelle branche. Le site web ne reflète donc pas forcément la branche principale.
</details>

Pour que le site web reflète toujours la branche principale, vous pouvez ajouter des règles à votre job `pages` pour qu'il ne s'exécute que sur cette branche. Par exemple :

```yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```
