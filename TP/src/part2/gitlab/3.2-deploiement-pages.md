# Déployer un site statique avec GitLab Pages

Avoir un livre de cuisine numérique, c’est bien. Mais le rendre agréable à consulter et accessible en ligne, c’est encore mieux !
**GitLab Pages** permet d’héberger facilement un site web statique directement à partir des fichiers de votre dépôt.

---

### Objectifs

* Faire bénéficier le dépôt collaboratif de la vérification Grammalecte.
* Générer automatiquement un site statique à partir des fichiers Markdown.
* Déployer ce site avec GitLab Pages.
* Visualiser le site web hébergé et itérer sur le contenu.

---

## Étape 0 — Coordination avec votre équipe

<div class="warning">
Vous travaillez ici sur le **dépôt collaboratif** du livre de recettes.  
Assurez-vous d’être sur une branche dédiée et de vous coordonner avec vos camarades avant toute modification.
</div>

Avant de commencer, discutez au sein de votre équipe de la répartition des tâches :

* Qui crée ou modifie le pipeline ?
* Qui rédige ou corrige les recettes ?
* Qui valide les *merge requests* avant leur intégration dans la branche principale ?

Pensez à utiliser les **issues GitLab** pour organiser le travail et suivre l’avancement du projet.

Exemple :

```bash
git checkout -b ci-pages
```

---

## Étape 1 — Créer le fichier `.gitlab-ci.yml`

Tout comme dans l’exercice précédent, commencez par créer un fichier `.gitlab-ci.yml` à la racine de votre dépôt.
Ce fichier va définir les **étapes du pipeline CI/CD**, qui s’exécuteront automatiquement à chaque *push* selon les règles que vous préciserez.

Le _pipeline_ de déploiement de votre site comportera trois étapes (_stages_) :

```yml
stages:
  - lint
  - build
  - deploy
```

L’ordre des étapes est important : GitLab exécute les _jobs_ dans l’ordre où les étapes associées sont définies.

---

## Étape 1.1 — Étape de lint (vérification linguistique)

L’étape `lint` correspond à la vérification grammaticale et orthographique du contenu, comme vous l’avez déjà fait sur votre dépôt individuel.

Vous pouvez réutiliser le même job `grammaire_et_orthographe` en l’adaptant si nécessaire à la structure du dépôt collaboratif.

Exemple :

```yml
grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install https://gitlab.in2p3.fr/sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md
```

Vérifiez bien que le chemin `recettes/**/*.md` correspond à l’arborescence de votre dépôt.

---

## Étape 1.2 — Étape de build (génération du site)

L’étape `build` va transformer vos fichiers Markdown en un **site web statique**.
Pour cela, nous utiliserons [Astro](https://astro.build/), un générateur de site statique moderne.

Afin de simplifier la configuration, une image Docker préconfigurée contenant Astro et un modèle de site vous est fournie.
Vous pouvez l’utiliser directement dans votre job via la directive `image:`.

Exemple de job :

```yml
pages:
  stage: build
  image: registry.gitlab.com/<nom_du_projet>/astro-template:latest
  before_script:
    - npm install
  script:
    - npx astro build
```

<div class="warning">
Le nom du job `pages` est **spécial** dans GitLab CI : il indique que ce job servira à **déployer le site avec GitLab Pages**.  
Si vous choisissez un autre nom, il faudra ajouter une configuration spécifique pour signaler à GitLab que ce job est destiné au déploiement Pages.
</div>

### Ajouter les artefacts de build

GitLab doit savoir quels fichiers seront publiés sur le site.
Astro génère le site dans un dossier nommé `public/`. Il faut donc indiquer à GitLab que ce dossier doit être conservé comme artefact après le job `build` :

```yml
  artifacts:
    paths:
      - public
```

<div class="warning">
GitLab Pages publie **par défaut** le contenu du dossier `public/`.  
Si vous changez le nom du dossier de sortie, vous devrez le spécifier explicitement dans la configuration du job.
</div>

---

## Étape 1.3 — Étape de déploiement

Bonne nouvelle : si votre job de build s’appelle `pages` et que le dossier `public/` est bien défini comme artefact, **GitLab s’occupe automatiquement du déploiement**.

Aucune étape supplémentaire n’est nécessaire pour que le site soit mis en ligne via GitLab Pages.
Dès que le pipeline se termine avec succès, GitLab héberge la version générée de votre site.

Exemple de pipeline complet minimal :

```yml
stages:
  - lint
  - build
  - deploy

grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git@gitlab.in2p3.fr:sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md

pages:
  stage: build
  image: registry.gitlab.com/<nom_du_projet>/astro-template:latest
  before_script:
    - npm install
  script:
    - npx astro build
  artifacts:
    paths:
      - public
```

## Étape 2 — Visualiser le site web et itérer

Une fois le pipeline terminé avec succès, rendez-vous dans les **paramètres du projet GitLab → Pages**.
Vous y trouverez le lien vers votre site web hébergé, du type :

```
https://<votre-groupe>.gitlab.io/<nom-du-projet>/
```

Cliquez dessus pour visualiser la version publiée de votre livre de recettes.

---

### Comprendre les mises à jour du site

Que se passe-t-il si plusieurs membres de l’équipe poussent des modifications en même temps ?
Le site est-il mis à jour automatiquement ? Et à partir de quelle branche ?

<details>
<summary>Réponse</summary>
Si aucune règle n’est définie, GitLab Pages déploie le site à chaque fois qu’un pipeline aboutit avec succès, quelle que soit la branche.  
Cela signifie que le site peut refléter une version non validée ou issue d’une branche de travail.
</details>

Pour garantir que le site corresponde toujours à la version principale du projet, il est préférable de **limiter le déploiement à la branche `main`**.

Ajoutez donc le bloc `rules:` suivant dans le job `pages` :

```yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

Grâce à cette règle :

* Les builds lancés depuis des branches secondaires (comme `feature/ajout-recette`) ne seront pas déployés.
* Le site ne sera mis à jour que lorsqu’une *merge request* est fusionnée dans `main`.

### Étape 3 — Itérer et améliorer le site

Une fois le site en ligne, vous pouvez :

* enrichir le texte et les métadonnées (titres, auteurs, tags de recettes) ;
* ajouter des images ;


Chaque nouvelle modification suivra le même cycle :
**commit → push → pipeline → déploiement automatique.**
