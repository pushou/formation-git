# Créer et inspecter un pipeline GitLab CI — Vérification d’orthographe avec Grammalecte

Dans cette étape, vous allez mettre en place une intégration continue (CI) sur GitLab qui vérifie automatiquement l’orthographe et certaines règles typographiques de vos recettes rédigées en Markdown à l’aide de [Grammalecte](https://grammalecte.net/).

### Objectifs

* Ajouter un fichier de pipeline `.gitlab-ci.yml` dans votre dépôt.
* Installer et exécuter Grammalecte en CI pour analyser `recettes/**/*.md` (c’est-à-dire tous les fichiers Markdown du dossier `recettes/` et de ses sous-dossiers).
* Faire échouer le pipeline si des erreurs sont détectées.
* Visualiser le pipeline et consulter les rapports dans l’interface GitLab.

---

## Pré-requis

* Un dépôt GitLab fonctionnel (dans un premier temps, votre carnet de recettes individuel).
* Au moins une recette en Markdown dans le dossier `recettes/` (par exemple : `recettes/crepes-classiques.md`).

---

## Étape 0 — Préparation

Avant de commencer, assurez-vous d’avoir synchronisé l’ensemble de votre travail avec le dépôt distant sur GitLab.

```bash
git pull origin main
```

Créez ensuite une branche dédiée à cet exercice, afin de ne pas impacter directement la branche principale :

```bash
git checkout -b ci-grammalecte
```

---

## Étape 1 — Créer le fichier `.gitlab-ci.yml`

À la racine de votre dépôt, créez un fichier nommé `.gitlab-ci.yml`.
Ce fichier décrit les différentes étapes (ou *stages*) que GitLab exécutera automatiquement sur ses *runners* (des machines virtuelles qui exécutent vos jobs CI/CD).

GitLab détecte automatiquement ce fichier lorsqu’il est présent à la racine du projet, et déclenche un pipeline à chaque *push* sur une branche contenant un tel fichier.

Dans un premier temps, nous allons définir une seule étape appelée `lint`, chargée de vérifier la qualité du texte.

<details>
<summary>Structure minimale</summary>

```yml
stages:
  - lint
```

</details>

### Définir le job d’analyse

L’étape `lint` contiendra un seul *job*, nommé `grammaire_et_orthographe`, qui analysera le contenu des recettes.
Comme Grammalecte est un package Python, nous utiliserons une image Docker basée sur Python.

<details>
<summary>Définition du job</summary>

```yml
grammaire_et_orthographe:
  stage: lint
  image: python:3.12
```

</details>

### Installer Grammalecte

Nous devons maintenant installer l’utilitaire de vérification.
La commande d’installation est la suivante :

```bash
python -m pip install git@gitlab.in2p3.fr:sonny.lion/grammalint.git
```

Nous plaçons cette commande dans un bloc `before_script`, ce qui permet de séparer proprement l’installation de l’exécution du code (c’est uniquement une question de clarté).

<details>
<summary>Ajout de la phase d’installation</summary>

```yml
grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git@gitlab.in2p3.fr:sonny.lion/grammalint.git
```

</details>

### Exécuter l’analyse

Pour lancer la vérification d’un fichier Markdown spécifique :

```bash
python -m grammalint -i recettes/crepes-classiques.md
```

Pour analyser automatiquement tous les fichiers Markdown du dossier `recettes/` (y compris ceux dans des sous-dossiers) :

```bash
python -m grammalint -i recettes/**/*.md
```

Le pipeline complet devient donc :

<details>
<summary>Pipeline complet</summary>

```yml
stages:
  - lint

grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git@gitlab.in2p3.fr:sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md
```

</details>

## Étape 2 — Commit, push et inspection du pipeline

Une fois votre fichier `.gitlab-ci.yml` créé, il est temps de le tester.

### 1. Enregistrer et envoyer les modifications

Ajouter vos modifications, créez un commit, puis poussez vos modifications sur le dépôt distant :

```bash
git add .gitlab-ci.yml
git commit -m "CI: vérification d’orthographe avec Grammalecte"
git push origin ci-grammalecte
```

Vérifiez que vous êtes bien sur la bonne branche avant de pousser :

```bash
git status
```

---

### 2. Visualiser le pipeline dans GitLab

1. Connectez-vous à l’interface web de votre projet GitLab.
2. Ouvrez le menu latéral **CI/CD → Pipelines**.
3. Vous devriez voir apparaître un pipeline, déclenché automatiquement par votre *push* sur la branche `ci-grammalecte`.

Chaque pipeline correspond à une exécution du fichier `.gitlab-ci.yml`.
Ici, il contient une seule étape : **`lint`**, et un seul job : **`grammaire_et_orthographe`**.

Si le pipeline ne s’exécute pas, vérifiez que :

* votre fichier s’appelle bien `.gitlab-ci.yml` (avec le point en début de nom) ;
* il est placé à la racine du dépôt ;
* votre push a bien été effectué sur GitLab.

---

### 3. Consulter les logs du job

Cliquez sur le job `grammaire_et_orthographe` pour afficher les logs.
Vous verrez :

* Le téléchargement de l’image Docker `python:3.12`.
* L’installation du paquet `grammalint`.
* L’analyse de vos fichiers Markdown.

Si tout se passe bien, vous verrez un message du type :

```
Analyse du fichier recettes/crepes-classiques.md
...
Job succeeded
```

Dans le cas contraire, le job échouera (`Job failed`) et les erreurs détectées apparaîtront dans les logs, par exemple :

```
...
Job failed
```

En cas d’échec, GitLab affichera un indicateur rouge sur le pipeline. Cela signifie que le job s’est arrêté avec un code d’erreur.

---

### 4. Corriger et rejouer le pipeline

Si des erreurs sont signalées :

1. Corrigez vos fichiers Markdown localement.
2. Commitez les modifications :

   ```bash
   git add recettes/
   git commit -m "Corrections orthographiques"
   git push
   ```
3. GitLab relancera automatiquement un **nouveau pipeline** après chaque *push*.

Vous pouvez aussi relancer manuellement un pipeline depuis **CI/CD → Pipelines → Retry**, pour réexécuter un job sans modifier le code.

## Étape 3 — Conditionner l’exécution du job

Par défaut, le job s’exécute à chaque *push* sur n’importe quelle branche.
Vous pouvez restreindre son exécution à un sous-ensemble de branches (via des expressions régulières), au demande de fusion, ou encore à la branche principale `main`.

Ici, nous voulons exécuter le job uniquement :

* sur la branche principale `main` ;
* ou lors d’une *Merge Request* (MR) visant `main`.

Ajoutez le bloc suivant à votre job :

```yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"        # Exécution sur la branche main
    - if: $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"  # Exécution sur les MR vers main
```

Tentez l'expérience de pousser des modifications sur la branche `ci-grammalecte` : le job ne s’exécutera pas.

Une fois le pipeline réussi, vous pouvez fusionner la MR. GitLab exécutera alors un nouveau pipeline sur `main`.

## Étape 4 — Artefacts et rapports d’analyse

Les **artefacts** sont des fichiers produits par un job et conservés par GitLab (par exemple : rapports, journaux ou fichiers d’analyse).
Ils peuvent être téléchargés directement depuis l’interface web.

Pour générer un rapport JSON avec Grammalecte, modifiez votre bloc `script:` comme suit :

```yml
  script:
    - python -m grammalint -i recettes/**/*.md -o report.json
```

Puis ajoutez une section `artifacts:` pour indiquer à GitLab de conserver ce fichier :

```yml
  artifacts:
    paths:
      - report.json
    expire_in: 1 week  # Durée de conservation (optionnel mais recommandé pour éviter d'encombrer le stockage)
```

Le fichier `report.json` apparaîtra alors dans la page du job, sous l’onglet **Artifacts**, et sera téléchargeable.
Les artefacts peuvent aussi être utilisés pour transférer des fichiers entre différents jobs d’un même pipeline.
