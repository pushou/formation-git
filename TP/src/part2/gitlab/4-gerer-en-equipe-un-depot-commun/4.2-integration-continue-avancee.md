# Publier un livre de recettes en ligne avec _GitLab Pages_

Avoir un livre de cuisine numérique, c’est bien. Le rendre agréable à consulter et accessible en ligne, c’est encore mieux.

Dans un premier temps, vous allez mettre en place un système d’intégration continue similaire à celui utilisé pour votre dépôt individuel. Vous découvrirez ensuite la notion de déploiement continu (_Continuous Deployment_ ou CD). Grâce à _GitLab Pages_, vous pourrez héberger un [site web statique](https://fr.wikipedia.org/wiki/Page_web_statique) directement depuis votre dépôt GitLab et ainsi transformer vos fichiers Markdown en un véritable livre de recettes en ligne.

## Coordination d’équipe

Avant de commencer à modifier le dépôt collaboratif, prenez un moment pour lire le TP et discuter de ce qu'il faut faire avec votre brigade. En particulier, posez-vous la question de :

- qui prépare les tickets ?
- qui gère ou modifie le _pipeline_ ?
- qui modifie ou corrige les recettes ?
- qui valide les _merge requests_ avant leur intégration dans `main` ?

Utilisez les tickets pour suivre les tâches à réaliser et l’avancement du projet. N’oubliez pas de toujours travailler sur une branche dédiée.

## Définir le _pipeline_ de vérification

Comme dans le [chapitre précédent](/part2/gitlab/3-creer-et-administrer-son-propre-depot/3.2-integration-continue-basique.md), commencez par créer un fichier nommé `.gitlab-ci.yml` à la racine de votre dépôt.

Pour rappel, ce fichier décrit les **étapes du _pipeline_** qui seront exécutées automatiquement à chaque _push_ (ou selon les règles que vous aurez définies).

Nous allons d’abord introduire l’étape `lint`, dédiée à la vérification grammaticale et orthographique du contenu du livre.
En vous inspirant du _pipeline_ mis en place pour votre dépôt individuel, ajoutez le _job_ `grammaire_et_orthographe`.

Vous pouvez réutiliser le script de vérification existant, en veillant simplement à adapter le chemin vers vos recettes si nécessaire.

### Exercices

1. Assurez-vous que le _job_ `grammaire_et_orthographe` fonctionne correctement en lançant un _pipeline_.
2. Corrigez les erreurs détectées et ajustez votre script, puis relancez un _pipeline_ jusqu’à obtenir un résultat sans erreur.

## Générer et publier le site web

Maintenant que le contenu de votre livre est automatiquement vérifié, il est temps de le rendre accessible en ligne. Pour cela, vous allez configurer deux nouvelles étapes dans le _pipeline_ : `build` et `deploy`.

Le _pipeline_ final comprendra donc trois étapes :

```yml
stages:
  - lint
  - build
  - deploy
```

GitLab exécutera les _jobs_ dans cet ordre, étape par étape, du _lint_ jusqu’au _deploy_.

L’étape `build` a pour objectif de transformer les fichiers Markdown du livre en un **site web statique** — des pages HTML simples, sans base de données ni traitement côté serveur.
L’étape `deploy`, quant à elle, publiera ce site à l’aide du système intégré _GitLab Pages_.

Pour générer les pages web à partir de vos fichiers Markdown, vous utiliserez un générateur de site statique nommé [*Astro*](https://astro.build/). Pas d’inquiétude : vous n’avez pas besoin de devenir expert en Astro ni d’écrire du code. Une image Docker préconfigurée (incluant Astro et un modèle de site) vous sera fournie. Bien entendu, vous pouvez utiliser votre propre configuration si vous le souhaitez.

<div class="warning">
L’image Docker étant préconfigurée pour un usage spécifique, vos recettes doivent impérativement être au format Markdown, dans un dossier `recettes/` à la racine du dépôt.  
Pour bénéficier pleinement de la mise en page, veillez également à respecter les propriétés de l’en-tête YAML (métadonnées) du gabarit fourni.
</div>

### Configurer la construction du site

Pour générer le site web, Gitlab à besoin d’un _job_ spécifique nommé `pages`. Ce nom est réservé et permet à Gitlab de savoir que ce _job_ est destiné à publier un site via _GitLab Pages_.[^pages].

[^pages]: Il est maintenant possible d’utiliser un autre nom de _job_ pour le déploiement de pages, mais cela nécessite une configuration supplémentaire. Pour plus de détails, consultez la documentation officielle : https://docs.gitlab.com/user/project/pages/#user-defined-job-names


Ajoutez donc le _job_ `pages` dans votre fichier `.gitlab-ci.yml` :


```yml
pages:
  stage: build
  image: à définir quand le dépôt sera créé
  before_script:
    # Installer les dépendances
    - npm install
  script:
    # Générer le site web
    - npx astro build
  # ... suite à venir ...
```

Le _job_ est très similaire à celui que vous avez utilisé pour la vérification grammaticale, on retrouve en particulier :
- l'étape à laquelle il appartient (`build`) ;
- l’utilisation d’une image Docker spécifique (ici celle contenant Astro) ;
- une étape `before_script` pour installer les dépendances nécessaires ;
- une étape `script` pour exécuter la commande de génération du site.



### Définir les _artefacts_ à publier

Il faut maintenant informer GitLab des fichiers à publier une fois le site généré. La commande `npx astro build` crée un dossier `dist/` à la racine du dépôt, contenant tous les fichiers HTML, CSS, JavaScript et médias nécessaires au site web. Il ne vous reste plus qu’à indiquer à GitLab de conserver ce dossier après l’exécution du _job_ à l'aide de la directive `artifacts` vu précédemment:

```yml
  # ... job pages ...
  artifacts:
    paths:
      - dist
```

Problème : par défaut, _GitLab Pages_ s'attend à publier le contenu d'un dossier nommé `public/`. Pour utiliser un autre répertoire, il vous revient de le préciser explicitement dans la configuration en ajoutant la directive `pages` dans votre _job_ :

```yml
pages:
  # ... reste de la configuration ...
  pages:  # specifie le répertoire à publier (par défaut 'public/')
      publish: dist
```

### Déployer le site

Pour finaliser la publication du site, il ne vous reste qu'à envoyer votre fichier `.gitlab-ci.yml` modifié dans le dépôt et attendre que le _pipeline_ s’exécute. Dès qu’un _pipeline_ se termine avec succès, votre site est mis en ligne sans étape manuelle supplémentaire.

Voici un exemple complet de configuration minimale :
<details>

```yml
stages:
  - lint
  - build
  - deploy

grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git+https://gitlab.in2p3.fr/sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md

pages:
  stage: build
  image: registry.gitlab.com/<nom_du_projet>/astro-template:latest
  before_script:
    - npm install
  script:
    - npx astro build
  artifacts:
    paths:
      - dist
  pages:
      publish: dist
```

</details>




### Visualiser le site publié

Une fois le _pipeline_ exécuté avec succès, accédez à l'interface GitLab à la section **Deploy > Pages** de votre projet GitLab.
Vous y trouverez l’URL du site hébergé, généralement de la forme :

```
https://<votre-projet>-<votre-groupe>-<hash>.pages.in2p3.fr/
```

Cliquez sur ce lien pour visualiser votre livre de recettes en ligne.

## Informations complémentaires

### Contrôler les déploiements

Par défaut, _GitLab Pages_ déploie le site **après chaque _pipeline_ réussi**, quelle que soit la branche.
Cela peut conduire à publier des versions en cours de travail.

Pour éviter cela, restreignez le déploiement à la branche principale `main` en ajoutant une règle :

```yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"
```

Ainsi :

* seules les modifications fusionnées dans `main` seront déployées ;
* les _builds_ issus de branches secondaires seront simplement validés, sans publication.
