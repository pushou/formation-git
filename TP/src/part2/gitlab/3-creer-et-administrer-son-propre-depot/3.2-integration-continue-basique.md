# Les bases de l’intégration continue sur GitLab

Écrire des recettes, c’est bien. Bien les écrire, c’est encore mieux !
Le concept d’intégration continue (_Continuous Integration_, ou en abrégé CI) désigne l’automatisation de tâches de validation et de vérification. Cela permet, par exemple, de s’assurer que le contenu respecte certaines normes de qualité avant d’être fusionné dans la branche principale.

Dans notre cas, nous allons mettre en place une intégration continue qui vérifiera automatiquement l’orthographe, la grammaire et certaines règles typographiques de vos recettes rédigées en Markdown, à l’aide de [Grammalecte](https://grammalecte.net/).

## Préparation

Avant de commencer, assurez-vous que votre espace de travail local est propre (aucune modification en cours) et à jour (synchronisé avec le dépôt distant sur GitLab).

Créez ensuite une branche dédiée à la mise en place de l’intégration continue :

```bash
git checkout -b ci-grammalecte
```

## Créer le fichier `.gitlab-ci.yml`

L’intégration continue sur GitLab est configurée à l’aide d’un fichier YAML nommé `.gitlab-ci.yml`.

À la racine de votre dépôt, créez ce fichier :

```bash
touch .gitlab-ci.yml
```

Ce fichier décrit les différentes étapes (ou _stages_) que GitLab exécutera automatiquement sur ses [_runners_](https://docs.gitlab.com/runner/)[^custom-runners] — des machines virtuelles qui lancent vos _jobs_ CI/CD.
Ces étapes forment ce qu’on appelle un [_pipeline_](https://docs.gitlab.com/ci/pipelines/).

[^custom-runners]: Il est possible de configurer ses propres _runners_, mais pour ce TP nous utiliserons les _runners_ partagés mis à disposition par le CC-IN2P3.

Une fois le fichier `.gitlab-ci.yml` _poussé_ (_push_) sur le dépôt distant, GitLab le détecte automatiquement et exécute les étapes qu’il contient. Par défaut, GitLab lance le _pipeline_ à chaque _push_ sur n’importe quelle branche.

Dans un premier temps, nous allons définir une seule étape, appelée `lint`[^lint], chargée de vérifier la qualité du texte.
Ouvrez le fichier `.gitlab-ci.yml` avec votre éditeur préféré et ajoutez-y le contenu suivant :

[^lint]: C’est le nom généralement utilisé pour ce type d’étape dédiée à la vérification du code, mais rien ne vous empêche d’en choisir un autre.

```yml
stages:
  - lint
```

## Définir le _job_ d’analyse

L’étape `lint` comprendra un seul _job_, intitulé `grammaire_et_orthographe`, chargé d’analyser le contenu des recettes.
Ce _job_ nécessite un environnement Python afin d’exécuter Grammalecte. Pour simplifier la gestion d’environnements parfois hétérogènes (chaque _job_ ayant ses propres dépendances), GitLab CI/CD permet d’utiliser des [images Docker](https://hub.docker.com/).
Celles-ci offrent des environnements préconfigurés couvrant un large éventail de besoins.

Ici, nous utiliserons l’image officielle `python:3.12`, qui contient la dernière version de Python 3.12 :

```yml
grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  # ... d'autres instructions viendront ici plus tard ...
```

La propriété `image:` indique à GitLab d’utiliser cette image Docker pour exécuter le _job_, tandis que `stage:` précise l’étape à laquelle il appartient.

### Installer Grammalecte

Nous devons maintenant expliquer à GitLab comment installer Grammalecte dans l’environnement Python fourni par l’image Docker.
Nous utiliserons `pip`, le gestionnaire de paquets Python, pour installer une surcouche de Grammalecte nommée `grammalint`, disponible [ici](https://gitlab.in2p3.fr/sonny.lion/grammalint).

La commande d’installation est la suivante :

```bash
python -m pip install git+https://gitlab.in2p3.fr/sonny.lion/grammalint.git
```

Nous plaçons cette commande dans un bloc `before_script`, afin de séparer clairement la phase d’installation de celle d’exécution (question de lisibilité) :

```yml
grammaire_et_orthographe:
  # ... instructions précédentes ...
  before_script:
    - python -m pip install git+https://gitlab.in2p3.fr/sonny.lion/grammalint.git
  # ... d'autres instructions viendront ici plus tard ...
```

### Configurer l’analyse des fichiers

Une fois `grammalint` installé, il faut indiquer à GitLab comment lancer l’analyse des fichiers Markdown.

Pour vérifier un fichier spécifique :

```bash
python -m grammalint -i recettes/crepes-classiques.md
```

Pour analyser tous les fichiers Markdown du dossier `recettes/` (y compris ceux des sous-dossiers) :

```bash
python -m grammalint -i recettes/**/*.md
```

En intégrant cette seconde version à notre _pipeline_, le fichier complet devient :

```yml
stages:
  - lint

grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git+https://gitlab.in2p3.fr/sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md
```

## Mettre à l’épreuve le _pipeline_

Une fois votre fichier `.gitlab-ci.yml` prêt, il est temps de vérifier que tout fonctionne.
Pour cela, versionnez le fichier et _poussez_-le (_push_) sur le dépôt distant.
Rendez-vous ensuite dans l’interface web de GitLab, section **Build > Pipelines**, pour observer le _pipeline_ en action. Vous devriez voir une page similaire à celle-ci :

![Interface GitLab - Pipelines](../../images/gitlab-pipelines.png)

Chaque ligne correspond à un _pipeline_ exécuté sur votre dépôt.
La colonne **Status** indique son état (en cours, réussi, échoué, etc.), tandis que **Stages** affiche les différentes étapes et leur statut.

Si le _pipeline_ ne s’exécute pas, vérifiez que :

- le fichier s’appelle bien `.gitlab-ci.yml` (avec le point au début) ;
- il est placé à la racine du dépôt ;
- votre _push_ a bien été effectué sur GitLab.

## Consulter les journaux du _pipeline_

Si votre _pipeline_ est en cours, patientez quelques instants puis actualisez la page pour voir le résultat.
En cas de succès, une icône verte avec une coche apparaîtra dans la colonne **Status** ; en cas d’échec, une croix rouge.

Pour comprendre ce qui s’est passé durant l’exécution, cliquez sur le statut du _pipeline_ (l’icône verte ou rouge) afin d’accéder à sa page de détails :

![Détails du pipeline GitLab](../../images/gitlab-pipeline-details.png)

Vous y verrez la liste des étapes (_stages_) et des _jobs_ associés.
Cliquez sur le _job_ `grammaire_et_orthographe` pour afficher les journaux (_logs_).

L’ordre d’exécution typique est le suivant :

- Téléchargement de l’image Docker `python:3.12`
- Installation du paquet `grammalint`
- Analyse des fichiers Markdown

Une fois l’analyse terminée, le message suivant indique que tout s’est bien déroulé :

```text
...
Job succeeded
```

En revanche, si Grammalecte a détecté des erreurs dans vos fichiers, le _job_ se terminera ainsi :

```text
10 min
^^^^^^
* 1 [0:6]  # #1117p / unit_nbsp_avant_unités1:
  Avec une unité de mesure, mettez un espace insécable.
  > Suggestions : 10 min

...

ERROR: Job failed: exit code 1
```

Enfin, le _job_ peut échouer avant même d’exécuter Grammalecte, par exemple si l’installation de `grammalint` échoue ou si le fichier `.gitlab-ci.yml` est mal formé.
Dans ce cas, n’hésitez pas à nous demander de l’aide.

## Corriger et rejouer le _pipeline_

Si des erreurs sont signalées, demandez-vous : s’agit-il de fautes réelles (orthographe, grammaire, typographie) ou de faux positifs ?
Cette réflexion est essentielle : en intégration continue, il ne faut pas corriger mécaniquement, mais comprendre la cause et la pertinence de chaque alerte.

Selon les erreurs détectées :

1. Corrigez vos fichiers Markdown localement (ou ajustez la configuration de Grammalecte si nécessaire).
2. Versionnez les modifications, puis effectuez un nouveau _push_.
3. GitLab relancera automatiquement un **nouveau _pipeline_**.

## Artefacts et rapports d’analyse

Les **artefacts** sont des fichiers produits par un _job_ (rapports, journaux, fichiers d’analyse, etc.) et conservés par GitLab.
Ils peuvent être téléchargés directement depuis l’interface web.

Pour générer un rapport JSON avec Grammalecte, modifiez le bloc `script:` ainsi :

```yml
# ... instructions précédentes ...
script:
  - python -m grammalint -i recettes/**/*.md -o report.json
```

Puis ajoutez une section `artifacts:` pour conserver le fichier :

```yml
# ... instructions précédentes ...
artifacts:
  paths:
    - report.json
  expire_in: 1 week # Durée de conservation (optionnelle, mais recommandée pour éviter l’encombrement du stockage)
```

Le fichier `report.json` apparaîtra alors dans la page du _job_, sous l’onglet **Artifacts**, et pourra être téléchargé.
Il est également possible de récupérer tous les artefacts d’un _pipeline_ depuis la page listant les _pipelines_.

Nous le verrons plus en détail dans la prochaine séquence, mais notez que les artefacts peuvent aussi être utilisés pour transférer des fichiers entre différents _jobs_ d’un même _pipeline_.

## Conclusion

Dans ce TP, nous avons découvert comment GitLab permet de mettre en place une **intégration continue** simple mais efficace pour nos projets. Nous avons appris à :

- Définir un _pipeline_ d’intégration continue avec le fichier `.gitlab-ci.yml`
- Créer et configurer un _job_ d’analyse automatique avec Grammalecte
- Surveiller l’exécution du _pipeline_ et interpréter les résultats dans l’interface GitLab
- Générer et consulter des rapports d’analyse sous forme d’artefacts

Avec ces notions, nous disposons désormais d’un outil capable de vérifier automatiquement la qualité de nos fichiers Markdown à chaque modification.

Dans la prochaine séquence, nous irons plus loin en découvrant comment enchaîner plusieurs _jobs_, gérer des dépendances entre étapes et construire des _pipelines_ plus complets et adaptés à des projets collaboratifs.

## Informations complémentaires

### Conditionner l’exécution d’un _job_

Par défaut, les _jobs_ s’exécutent à chaque _push_ sur n’importe quelle branche.
Vous pouvez toutefois restreindre leur exécution à certaines branches, aux _Merge Requests_ (MR), ou encore à la branche principale `main`.
Cela permet d’éviter une utilisation excessive des ressources des _runners_ et de réduire le temps d’exécution des _pipelines_.

Par exemple, si vous avez un _job_ de test long que vous ne souhaitez exécuter que :

- sur la branche `main` ;
- ou lors d’une _Merge Request_ visant `main` ;

ajoutez simplement ce bloc :

```yml
# ... instructions précédentes ...
rules:
  - if: $CI_COMMIT_BRANCH == "main" # Exécution sur la branche principale
  - if: $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main" # Exécution sur les MR vers main
```
