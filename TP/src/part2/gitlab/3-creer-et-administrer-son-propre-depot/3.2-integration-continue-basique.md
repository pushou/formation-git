# Les bases de l’intégration continue sur GitLab

Ecrire des recettes, c’est bien. Bien les écrire, c’est mieux ! Le concept d’intégration continue (_Continuous Integration_, ou en abrégé CI) désigne l’automatisation de tâches de validation et de vérification. Cela permet par exemple de s’assurer que le contenu respecte certaines normes de qualité avant d’être fusionné dans la branche principale.

Dans notre cas, nous allons mettre en place une intégration continue qui vérifiera automatiquement l’orthographe, la grammaire et certaines règles typographiques de vos recettes rédigées en Markdown à l’aide de [Grammalecte](https://grammalecte.net/).


## Préparation

Avant de commencer, assurez-vous que votre espace de travail local est propre (pas de modifications en cours) et à jour (synchronisé avec le dépôt distant sur GitLab).

Créez ensuite une branche dédiée à la mise en place de l’intégration continue :

```bash
git checkout -b ci-grammalecte
```

## Créer le fichier `.gitlab-ci.yml`

L'intégration continue sur GitLab est configurée à l’aide d’un fichier YAML nommé `.gitlab-ci.yml`.

À la racine de votre dépôt, créez un fichier nommé `.gitlab-ci.yml` :

```bash
touch .gitlab-ci.yml
```

Ce fichier décrit les différentes étapes (ou _stages_) que GitLab exécutera automatiquement sur ses [_runners_](https://docs.gitlab.com/runner/)[^custom-runners] (des machines virtuelles qui exécutent vos jobs CI/CD). Ces étapes forment ce qu’on appelle communément un [_pipeline_](https://docs.gitlab.com/ci/pipelines/). 

[^custom-runners]: Il est possible de configurer ses propres _runners_, mais pour ce TP nous utiliserons les _runners_ partagés mis à disposition par le CC-IN2P3.

Une fois le fichier `.gitlab-ci.yml` poussé sur le dépôt distant, GitLab le détecte automatiquement et exécute les étapes qu’il contient. Par défaut, Gitlab execute le pipeline à chaque _push_ sur n’importe quelle branche.

Dans un premier temps, nous allons définir une seule étape appelée `lint`[^lint], chargée de vérifier la qualité du texte. Ouvrez le fichier `.gitlab-ci.yml` avec votre éditeur de texte préféré et ajoutez-y le contenu suivant :

[^lint]: C'est le nom généralement utilisé pour ce type d'étape dédiée à la vérification de code mais rien ne vous empêche de choisir un autre nom

```yml
stages:
  - lint
```

## Définir le _job_ d’analyse

L’étape `lint` comprendra un seul _job_, intitulé `grammaire_et_orthographe`, chargé d’analyser le contenu des recettes. Ce _job_ nécessite un environnement disposant de Python afin d’exécuter Grammalecte. Pour simplifier l’exécution de _jobs_ parfois hétérogènes, chacun ayant ses propres dépendances, GitLab CI/CD permet d’utiliser des [images Docker](https://hub.docker.com/). Celles-ci offrent des environnements préconfigurés couvrant un large éventail de besoins.

Ici, nous utiliserons l’image officielle `python:3.12`, qui contient la dernière version de Python 3.12 :

```yml
grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  # ... d'autres instructions viendront ici plus tard ...
```

La propriété `image:` indique à GitLab d’utiliser cette image Docker pour exécuter le _job_ tandis que `stage:` spécifie l’étape à laquelle ce _job_ appartient.


### Configurer l’installation de Grammalecte

Nous devons maintenant expliquer à GitLab comment installer Grammalecte dans l’environnement Python fourni par l’image Docker. Nous utiliserons `pip`, le gestionnaire de paquets Python, pour installer une surcouche de Grammalecte nommée `grammalint` disponible [ici](https://gitlab.in2p3.fr/sonny.lion/grammalint).

Pour installer `grammalint`, la commande est la suivante :

```bash
python -m pip install https://gitlab.in2p3.fr/sonny.lion/grammalint.git
```

Nous plaçons cette commande dans un bloc `before_script`, ce qui permet de séparer proprement l’installation de l’exécution du code (c’est uniquement une question de clarté).


```yml
grammaire_et_orthographe:
  # ... instructions précédentes ...
  before_script:
    - python -m pip install https://gitlab.in2p3.fr/sonny.lion/grammalint.git
  # ... d'autres instructions viendront ici plus tard ...
```


### Configurer l’analyse des fichiers

Une fois `grammalint` installé, il faut indiquer à GitLab comment lancer l’analyse des fichiers Markdown.

On peut lancer la vérification d’un fichier Markdown spécifique, avec la commande suivante :

```bash
python -m grammalint -i recettes/crepes-classiques.md
```

Il est aussi possible d'analyser tous les fichiers Markdown du dossier `recettes/` (y compris ceux dans des sous-dossiers) avec cette variante :

```bash
python -m grammalint -i recettes/**/*.md
```

En intégrant cette deuxième version à notre _pipeline_, le fichier `.gitlab-ci.yml` complet devient :


```yml
stages:
  - lint

grammaire_et_orthographe:
  stage: lint
  image: python:3.12
  before_script:
    - python -m pip install git@gitlab.in2p3.fr:sonny.lion/grammalint.git
  script:
    - python -m grammalint -i recettes/**/*.md
```



## Mettre à l’épreuve le pipeline

Une fois votre fichier `.gitlab-ci.yml` créé, il est temps de le tester.

### Versionner et envoyer les modifications

Ajouter vos modifications, créez un commit, puis poussez vos modifications sur le dépôt distant



### 2. Visualiser le pipeline dans GitLab

1. Connectez-vous à l’interface web de votre projet GitLab.
2. Ouvrez le menu latéral **CI/CD → Pipelines**.
3. Vous devriez voir apparaître un pipeline, déclenché automatiquement par votre *push* sur la branche `ci-grammalecte`.

Chaque pipeline correspond à une exécution du fichier `.gitlab-ci.yml`.
Ici, il contient une seule étape : **`lint`**, et un seul job : **`grammaire_et_orthographe`**.

Si le pipeline ne s’exécute pas, vérifiez que :

* votre fichier s’appelle bien `.gitlab-ci.yml` (avec le point en début de nom) ;
* il est placé à la racine du dépôt ;
* votre push a bien été effectué sur GitLab.


### 3. Consulter les _logs_ du job

Cliquez sur le job `grammaire_et_orthographe` pour afficher les logs.
Vous verrez :

* Le téléchargement de l’image Docker `python:3.12`.
* L’installation du paquet `grammalint`.
* L’analyse de vos fichiers Markdown.

Si tout se passe bien, vous verrez un message du type :

```
Analyse du fichier recettes/crepes-classiques.md
...
Job succeeded
```

Dans le cas contraire, le job échouera (`Job failed`) et les erreurs détectées apparaîtront dans les logs, par exemple :

```
...
Job failed
```

En cas d’échec, GitLab affichera un indicateur rouge sur le pipeline. Cela signifie que le job s’est arrêté avec un code d’erreur.


### 4. Corriger et rejouer le pipeline

Si des erreurs sont signalées :

1. Corrigez vos fichiers Markdown localement.
2. Commitez les modifications :

   ```bash
   git add recettes/
   git commit -m "Corrections orthographiques"
   git push
   ```
3. GitLab relancera automatiquement un **nouveau pipeline** après chaque *push*.

Vous pouvez aussi relancer manuellement un pipeline depuis **CI/CD → Pipelines → Retry**, pour réexécuter un job sans modifier le code.


## Étape 3 — Conditionner l’exécution du job

Par défaut, le job s’exécute à chaque *push* sur n’importe quelle branche.
Vous pouvez restreindre son exécution à un sous-ensemble de branches (via des expressions régulières), aux demandes de fusion, ou encore à la branche principale `main`.

Ici, nous voulons exécuter le job uniquement :

* sur la branche principale `main` ;
* ou lors d’une *Merge Request* (MR) visant `main`.

Ajoutez le bloc suivant à votre job :

```yml
  rules:
    - if: $CI_COMMIT_BRANCH == "main"        # Exécution sur la branche main
    - if: $CI_MERGE_REQUEST_TARGET_BRANCH_NAME == "main"  # Exécution sur les MR vers main
```

Tentez l'expérience de pousser des modifications sur la branche `ci-grammalecte` : le job ne s’exécutera pas.

Une fois le pipeline réussi, vous pouvez fusionner la MR. GitLab exécutera alors un nouveau pipeline sur `main`.


## Étape 4 — Artefacts et rapports d’analyse

Les **artefacts** sont des fichiers produits par un job et conservés par GitLab (par exemple : rapports, journaux ou fichiers d’analyse).
Ils peuvent être téléchargés directement depuis l’interface web.

Pour générer un rapport JSON avec Grammalecte, modifiez votre bloc `script:` comme suit :

```yml
  script:
    - python -m grammalint -i recettes/**/*.md -o report.json
```

Puis ajoutez une section `artifacts:` pour indiquer à GitLab de conserver ce fichier :

```yml
  artifacts:
    paths:
      - report.json
    expire_in: 1 week  # Durée de conservation (optionnel mais recommandé pour éviter d'encombrer le stockage)
```

Le fichier `report.json` apparaîtra alors dans la page du job, sous l’onglet **Artifacts**, et sera téléchargeable.
Les artefacts peuvent aussi être utilisés pour transférer des fichiers entre différents jobs d’un même pipeline.



Téléchargez ensuite le fichier depuis l’onglet **Artifacts** de la page du job. Les artefacts peuvent aussi servir à partager des fichiers entre plusieurs jobs d’un même pipeline.

## Conclusion

Vous avez configuré un pipeline GitLab CI simple pour analyser automatiquement l’orthographe et la grammaire de vos recettes Markdown. Vous savez maintenant où consulter les pipelines, interpréter les journaux, corriger et relancer les jobs, restreindre l’exécution à `main` et publier des artefacts d’analyse.
